## Executive Summary

Currently, every binary generated by the Nizam/Mantiq self-hosted compiler links against a monolithic, ~4,000-line C runtime library ([mantiq/runtime.c](file:///home/red-x/projects/desktop/mantiq_nizam/mantiq/runtime.c) compiled to `runtime.o` and `runtime_wasm.o`). While this C runtime was indispensable during initial Stage 0 bootstrapping (when the compiler was written in Zig and lacked self-hosted container and memory management implementations), it now poses a foundational architectural bottleneck.

This proposal sets forth the rationale, subsystem deconstruction, and phased implementation plan to **completely eliminate the monolithic C runtime**, transitioning Nizam and Mantiq into a **Zero-Runtime (or Micro-Runtime / Pure-Standard-Library) Systems Language** akin to Zig, Rust, and modern C++.

## 1. Anatomy of the Current Runtime (`runtime.c`)

The current [mantiq/runtime.c](file:///home/red-x/projects/desktop/mantiq_nizam/mantiq/runtime.c) acts as an omnibus catch-all library containing several disjoint responsibilities:

| Subsystem | Key Symbols in `runtime.c` | Current Implementation | Issues & Deficits |
| :--- | :--- | :--- | :--- |
| **Memory Management** | `mantiq_malloc`, `mantiq_free`, `mantiq_realloc`, `mantiq_calloc` | Wrappers around `sys_malloc` (mimalloc or libc `malloc`) | Global single-allocator model; cannot customize or isolate arenas; no allocation failure handling. |
| **Collections ABI** | `__mantiq_list_*`, `__mantiq_dict_*`, `__mantiq_set_*` | Untyped `void*` buffer reallocations, open-addressing hash table in C | Type-erased; requires `void*` casts; LLVM cannot inline or optimize accesses; causes ABI alignment bugs. |
| **Concurrency & Actors** | `mantiq_spawn`, `mantiq_await`, `mantiq_channel_*`, `__mantiq_parallel_for` | POSIX `pthread`, mutexes, condition variables, ring buffers | Unusable in bare-metal or single-threaded WASM; forces `pthread` linking on all targets; heavy thread spawning. |
| **Strings & Text** | `mantiq_string_compare`, `mantiq_string_concat`, formatting helpers | `memcpy`, `snprintf`, manual byte loops | Duplicates pure Nizam implementations in [std/string.nz](file:///home/red-x/projects/desktop/mantiq_nizam/mantiq/std/string.nz). |
| **Standard I/O & OS** | `mantiq_print_*`, `mantiq_read_input`, `mantiq_process_args` | `printf`, `fgets`, `/proc/self/cmdline` reading | Unbuffered stdout calls; POSIX-specific `/proc` dependency breaks non-Linux targets. |
| **Domain-Specific Logic** | `quantum_qreg`, `quantum_h`, `quantum_cnot`, `mantiq_run_qasm` | 16-qubit state-vector simulator ($2^{16} = 65,536$ complex pairs) | Injects ~1 MB static memory and libm math dependencies into every compiled program, even simple scripts. |
| **Compile-Time Helpers** | `mantiq_temp_tracker_*`, `mantiq_codegen_temp`, `mantiq_codegen_alloc` | Global dynamic arrays for tracking SSA temps during codegen | Bootstrap artifact: compile-time helpers residing in runtime binary. |

## 2. WHY We Must Eliminate the Runtime

### 2.1 The "Split-Brain" Type System & Self-Hosting Integrity
A programming language that aspires to be modern and self-hosted cannot rely on another language's runtime to execute its own core data structures. Currently:
- Nizam defines `struct List[T]` and `struct Dict[K, V]` in [mantiq/std/collections.nz](file:///home/red-x/projects/desktop/mantiq_nizam/mantiq/std/collections.nz) and `struct String` in [mantiq/std/string.nz](file:///home/red-x/projects/desktop/mantiq_nizam/mantiq/std/string.nz).
- Yet [mantiq/src/codegen.nz](file:///home/red-x/projects/desktop/mantiq_nizam/mantiq/src/codegen.nz) regularly emits calls to external C shims: `__mantiq_list_append`, `__mantiq_dict_get`, `mantiq_free`.
- This creates two conflicting definitions of the same data structure: one in pure Nizam and one in C. Any change to memory layout, padding, or alignment in Nizam requires manually synchronizing C structs in `runtime.c`, which frequently introduces subtle memory corruption.

### 2.2 Safety, Lifetimes & Borrow Checking Integrity
Nizam features an **affine type system** with move semantics, auto-drops, dynamic stack drop flags, and a relational Polonius borrow checker ([mantiq/src/borrowck.nz](file:///home/red-x/projects/desktop/mantiq_nizam/mantiq/src/borrowck.nz)).
- **C has no knowledge of affine types**: Inside `runtime.c`, references are converted to raw `void*`, sizes are manipulated with `size_t`, and elements are copied with `memcpy`.
- If a collection in `runtime.c` frees or reallocates memory, Nizam's borrow checker cannot track whether references to elements have been invalidated.
- Implementing collections in pure Nizam ensures that all operations obey borrow-checker invariants, drops are tracked via compiler-generated drop flags, and memory leaks are provably avoided.

### 2.3 The Inlining & Monomorphization Bottleneck (Optimization Deficit)
When Nizam calls into `runtime.o`:
```llvm
call ptr @__mantiq_list_append(ptr %list, ptr %elem, i64 8)
```
- To LLVM, this is an **opaque call barrier**. LLVM must assume the call may clobber any heap memory, escape pointers, or read arbitrary global state.
- **No inlining**: Simple operations (like index calculations or vector push without resize) cannot be inlined into hot loops.
- **No escape analysis**: An allocation passed to a C function cannot be promoted to stack memory by LLVM.
- **No auto-vectorization**: Homogeneous numerical loops cannot be vectorized using SIMD instructions because `runtime.c` operates on `void*`.

In contrast, if `List[T]` is written in pure Nizam and monomorphized:
- `list.append(x)` expands directly into an inline check (`if len < cap: data[len] = x; len++`), which LLVM can unroll and vectorize with AVX2/NEON.
- When an object does not escape a function, LLVM can completely eliminate the allocation.

### 2.4 Binary Bloat & Executable Footprint
Every single binary produced by `nizam build` currently links `runtime.o`, pulling in:
- The 16-qubit quantum state vector ($65,536 \times 16 \text{ bytes} \approx 1\text{ MB}$ of static `.bss`/data).
- `pthread`, `libm` (math library), and C runtime startup stubs.
- Unused hash table and actor dispatch tables.

A trivial command-line utility or "Hello World" binary ends up megabytes in size instead of a lean 15–30 KB.

### 2.5 Freestanding, Embedded & Bare-Metal Targets (`#no_std`, WASM, Kernels)
The reliance on `runtime.c` makes targeting non-standard environments difficult:
- **WebAssembly**: Requires stubs for `ioctl`, `pthread`, and POSIX file descriptors, causing WASI/WASM build complications.
- **Bare-metal & Embedded**: Cannot compile because microcontrollers do not provide `pthread.h`, `sys/resource.h`, or POSIX memory allocators.
- **OS Kernels & Drivers**: Cannot link standard libc or arbitrary C runtimes.

Eliminating `runtime.c` allows Nizam to support a true `#no_std` mode with pluggable allocators.

### 2.6 Deterministic Bootstrapping & Toolchain Independence
Currently, building the Nizam compiler requires:
1. Compiling `runtime.c` with a host C compiler (`gcc` or `clang`).
2. Compiling `tree_sitter_helper.c`.
3. Synchronizing these objects via [dev-sync.sh](file:///home/red-x/projects/desktop/mantiq_nizam/dev-sync.sh).

Eliminating the runtime reduces the compiler's dependencies to just Nizam source files and the LLVM backend.

## 3. HOW We Will Eliminate the Runtime: Subsystem Deconstruction

We deconstruct the ~4,000 lines of [mantiq/runtime.c](file:///home/red-x/projects/desktop/mantiq_nizam/mantiq/runtime.c) into 5 clean, modular layers in pure Nizam and standard library modules:

```
┌────────────────────────────────────────────────────────────────────────┐
│                   Layer 4: Domain Extensions                           │
│  std.quantum (Optional Library) │ std.python_ffi (Optional Extension) │
├────────────────────────────────────────────────────────────────────────┤
│                   Layer 3: Concurrency & Async Engine                  │
│       std.sync (Channels, Mutexes, Semaphores via OS Futexes)          │
├────────────────────────────────────────────────────────────────────────┤
│                   Layer 2: Standard Collections & Text                 │
│      std.collections (List[T], Dict[K,V]) │ std.string (String)        │
├────────────────────────────────────────────────────────────────────────┤
│                   Layer 1: Pluggable Memory Architecture               │
│        std.mem (Allocator Interface: Page, Arena, Heap, Bump)          │
├────────────────────────────────────────────────────────────────────────┤
│                   Layer 0: OS Abstraction & Intrinsics                 │
│      std.sys (Direct Linux Syscalls / Win32 / WASI / LLVM Intrinsics)  │
└────────────────────────────────────────────────────────────────────────┘
```

---

### Layer 0: Direct OS Primitives & LLVM Intrinsics (`std.sys`)

Rather than routing through C standard library wrappers, low-level primitives map directly to:
1. **LLVM Intrinsics**:
   - Memory manipulation: `llvm.memcpy.*`, `llvm.memmove.*`, `llvm.memset.*`.
   - Atomics & Memory Fences: `atomicrmw`, `cmpxchg`, `fence`.
   - Math operations: `llvm.sqrt.*`, `llvm.sin.*`, `llvm.floor.*`.
2. **Direct System Calls / Platform ABIs**:
   - Linux: Native syscalls via inline assembly or `syscall` instruction (`sys_read`, `sys_write`, `sys_mmap`, `sys_munmap`, `sys_futex`, `sys_exit`).
   - WASI: Direct WASI imports (`fd_write`, `environ_sizes_get`).
   - Windows: Direct imports from `kernel32.dll` (`WriteFile`, `VirtualAlloc`, `VirtualFree`).

**Example: Pure Nizam OS Write (`std/sys.nz`)**:
```nizam
// ── Linux Syscall Implementation ───────────────────────────────────────
public fn sys_write(fd as i32, buf as ptr[u8], count as usize) as isize:
    #ifdef TARGET_LINUX_X86_64
    // Direct Linux syscall 1 (sys_write)
    return asm(
        "syscall"
        : "={rax}" (result)
        : "{rax}" (1), "{rdi}" (fd), "{rsi}" (buf), "{rdx}" (count)
        : "rcx", "r11", "memory"
    )
    #else
    // Fallback to minimal libc write symbol
    extern fn write(fd as i32, buf as ptr[u8], count as usize) as isize
    return write(fd, buf, count)
    #endif
```

### Layer 1: Pluggable Allocator Architecture (`std.mem`)

Currently, `runtime.c` hardcodes `mantiq_malloc` and `mantiq_free` directly to `malloc` / `free`. We replace this with a **first-class Allocator interface** in pure Nizam:

```nizam
// ── Allocator Interface ────────────────────────────────────────────────
struct Allocator:
    public var ptr_alloc as fn(ctx as ptr[u8], size as usize, align as usize) as ptr[u8]
    public var ptr_resize as fn(ctx as ptr[u8], old_ptr as ptr[u8], old_size as usize, new_size as usize) as ptr[u8]
    public var ptr_free as fn(ctx as ptr[u8], ptr as ptr[u8], size as usize)
    public var context as ptr[u8]

    public fn alloc(self as ptr[Allocator], size as usize, align as usize) as ptr[u8]:
        return ((deref self).ptr_alloc)((deref self).context, size, align)

    public fn free(self as ptr[Allocator], ptr as ptr[u8], size as usize):
        ((deref self).ptr_free)((deref self).context, ptr, size)
```

#### Standard Allocator Implementations:
1. **`PageAllocator`**:
   - Calls `mmap` / `VirtualAlloc` directly to request whole virtual memory pages from the OS kernel.
2. **`ArenaAllocator`**:
   - Wraps a backing allocator and allocates memory monotonically.
   - Deallocates all objects at once in `arena.deinit()`, providing $O(1)$ batch cleanup for compilers and request handlers.
3. **`HeapAllocator`**:
   - High-performance general-purpose heap allocator (e.g., ported mimalloc or embedded buddy allocator written in pure Nizam).
4. **`FixedBufferAllocator`**:
   - Uses a stack-allocated or static buffer with zero OS allocations; ideal for `#no_std` embedded systems.

### Layer 2: Generic Pure-Nizam Collections (`std.collections`)

The compiler will stop emitting calls to `__mantiq_list_*` and `__mantiq_dict_*`. Instead, `List[T]` and `Dict[K, V]` are compiled as standard generic Nizam structs.

#### Pure Nizam `List[T]` Implementation:
```nizam
struct List[T]:
    public var data as ptr[T]
    public var length as i64
    public var capacity as i64
    public var allocator as ptr[Allocator]

    public fn init(allocator as ptr[Allocator]) as List[T]:
        return List[T](
            data = None to ptr[T],
            length = 0 to i64,
            capacity = 0 to i64,
            allocator = allocator
        )

    public fn append(self as ptr[List[T]], item as T):
        if (deref self).length >= (deref self).capacity:
            let new_cap as i64 = if (deref self).capacity == 0 to i64: 8 to i64 else: (deref self).capacity * 2 to i64
            let item_sz as usize = sizeof[T]()
            let new_data as ptr[T] = ((deref self).allocator).resize(
                (deref self).data to ptr[u8],
                ((deref self).capacity to usize) * item_sz,
                (new_cap to usize) * item_sz
            ) to ptr[T]
            (deref self).data = new_data
            (deref self).capacity = new_cap
        
        let target as ptr[T] = (deref self).data + (deref self).length
        (deref target) = item
        (deref self).length = (deref self).length + 1 to i64
```

#### Benefits:
- **Full Inlining**: The `append` branch check is inlined directly into callers.
- **Type Safety**: Elements are preserved without `void*` casts.
- **Automatic Element Cleanup**: When `List[T]` drops, the compiler invokes `T`'s drop function on each active element before freeing the buffer.

### Layer 3: Concurrency, Fibers & Channels (`std.sync`)

Currently, `runtime.c` uses heavyweight OS threads (`pthread_create`), mutexes, and condition variables for channels and parallel loops.

#### Replacement Strategy:
1. **Lightweight Channel Ring Buffer in Pure Nizam**:
   - Implemented using atomic head/tail indices (`llvm.atomicrmw`).
2. **Futex-Based Thread Parking (`std.sync.futex`)**:
   - Direct Linux `sys_futex` / Windows `WaitOnAddress` calls eliminate the need for `pthread_mutex` and `pthread_cond` overhead.
3. **M:N Cooperative Coroutines / Fibers**:
   - Replace OS thread spawning for actor tasks (`mantiq_spawn`) with stackful fibers or async state machines, managed by a pure-Nizam work-stealing thread pool.

---

### Layer 4: Domain Extensions Decoupling

`runtime.c` currently forces domain-specific features into all programs:
1. **Quantum Simulation (`mantiq_quantum_init`, `quantum_qreg`, etc.)**:
   - Move to a separate package or optional module: `mantiq/std/quantum.nz`.
   - Programs that do not use quantum syntax (`qubit`, `qasm`, `H`, `CNOT`) incur **0 bytes** of memory or binary overhead.
2. **Python FFI Runtime Shims**:
   - Relocate Python C-API bindings into `mantiq/std/python.nz`.

### Layer 5: Eliminating Compile-Time Bootstrap Shims in `codegen.nz`

In [mantiq/src/codegen.nz](file:///home/red-x/projects/desktop/mantiq_nizam/mantiq/src/codegen.nz), lines 850–930 call:
- `mantiq_temp_tracker_push`
- `mantiq_temp_tracker_consume`
- `mantiq_codegen_temp`
- `mantiq_codegen_alloc`

These functions run *inside the compiler at compile-time* using `runtime.c`. We replace them with internal fields in `LLVMCodegen`:
```nizam
struct TempTracker:
    public var unconsumed_regs as List[String]
    public var unconsumed_types as List[String]

    public fn push(self as ptr[TempTracker], reg as String, ty as String):
        (deref self).unconsumed_regs.append(reg)
        (deref self).unconsumed_types.append(ty)
```
This decouples the compiler's own build process from `runtime.c`.

## 4. Compiler Transformations in `src/codegen.nz`

To support the zero-runtime model, `src/codegen.nz` will undergo five architectural updates:

1. **Remove Built-in External Declarations**:
   - Remove lines registering `mantiq_free`, `mantiq_malloc`, `__mantiq_list_append`, etc., from `(deref self).external_decls`.
2. **Synthesize Type-Specific Drop Functions (`@__nizam_drop_<T>`)**:
   - Codegen emits typed destructor functions for structs, strings, and collections in the module's LLVM IR:
     ```llvm
     define void @__nizam_drop_String(ptr %s) {
       %data = load ptr, ptr %s
       %cap = ...
       call void @std_mem_default_free(ptr %data, i64 %cap)
       ret void
     }
     ```
3. **Monomorphization Pipeline**:
   - Ensure `typecheck.nz` and `codegen.nz` monomorphize container ASTs (`List[i32]`, `List[String]`) and emit their methods directly into the translation unit or link them from precompiled `.o` library archives.
4. **Direct LLVM Intrinsic Mapping**:
   - Map memory clearing to `@llvm.memset.p0.i64`, memory copying to `@llvm.memcpy.p0.i64`, and pointer math to `getelementptr`.
5. **Freestanding Entry Point (`_start` vs `main`)**:
   - In `#no_std` mode, emit `_start` directly, initializing minimal stack and calling user `main` without C `crt0.o` or libc initializers.

## Conclusion

Eliminating `runtime.c` is the definitive step that will elevate Nizam from an experimental compiler into an industrial-grade, zero-overhead systems programming language. By replacing opaque C shims with pure Nizam abstractions in `std.mem`, `std.collections`, and `std.sync`, we achieve:
1. **Uncompromised memory safety** guarded by our Polonius borrow checker.
2. **Aggressive optimization** through LLVM inlining and monomorphization.
3. **Minimal binary footprints** free from domain-specific bloat.
4. **Universal portability** across embedded microcontrollers, kernels, and WebAssembly.
